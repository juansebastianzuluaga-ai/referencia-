# Reglas de negocio - Planes de Acción y Casos (ISO 9001:2015 cláusula 10.2.1)

## Tipos de Plan de Acción (`action_plan_types`)
Catálogo con al menos:
- code (CR = Corrección, AM = Acción de Mejora, AC = Acción Correctiva)
- name
- requires_root_cause_analysis (boolean)
- requires_effectiveness_review (boolean)
- is_legacy (boolean, default false): valores heredados de migraciones de datos (ej. "Preventiva") que no deben ofrecerse en formularios nuevos, solo para lectura/reportes históricos.

Regla (norma ISO 9001:2015, cláusula 10.2.1):
- CR (Corrección): requires_root_cause_analysis = false, requires_effectiveness_review = false. Es la reacción inmediata para controlar la no conformidad; no elimina la causa.
- AM (Acción de Mejora): requires_root_cause_analysis = false, requires_effectiveness_review = false. No deriva de una no conformidad.
- AC (Acción Correctiva): requires_root_cause_analysis = true, requires_effectiveness_review = true. Debe eliminar la causa raíz y su eficacia debe revisarse (única exigida explícitamente por la norma).

## Fuentes (`sources`)
Catálogo de orígenes: auditoria, riesgo, indicador, no_conformidad, comite, acta, pqrs, incidente, evento_adverso, analisis_grupal, adherencia, etc.

## Reglas de aprobación por fuente (`source_approval_rules`)
- source_id
- approver_user_id (o approver_role_id si se requiere por rol)
- registrar_user_id (o registrar_role_id)

## Análisis de Causa (`root_cause_analyses`)
- action_plan_id
- technique (five_whys, ishikawa, pareto) — valor técnico fijo, puede ser Enum
- description

Solo se crea cuando `action_plan_types.requires_root_cause_analysis = true`.

### Pasos del análisis (`root_cause_analysis_steps`)
- root_cause_analysis_id
- question (ej. cada "¿Por qué?" de la técnica 5 Porqués, o cada causa de Ishikawa/Pareto)
- order

Tabla hija en vez de un campo `json`, para que cada paso sea consultable/editable individualmente (coincide con el listado "Causa raíz" visto en el sistema viejo: ID + "Por qué" incremental).

## Revisión de Eficacia (`effectiveness_reviews`)
- action_plan_id
- responsible_user_id
- form_schema (json, formulario dinámico)
- form_data (json, respuestas)
- is_effective (boolean)
- reviewed_at

Solo se crea cuando `action_plan_types.requires_effectiveness_review = true`.

## Priorización (matriz GUT) en `action_plans`

Escala GUT clásica (subconjunto 1/3/5) almacenada en el catálogo `gut_levels`:
- dimension (Enum técnico fijo: severity, urgency, trend)
- code
- label (ej. "Muy grave", "Inmediata", "Saldrá de control")
- weight (1, 3 o 5)
- order

Campos en `action_plans`:
- severity_level_id -> gut_levels.id
- urgency_level_id -> gut_levels.id
- trend_level_id -> gut_levels.id
- priority_score (cacheado) = weight(severity) * weight(urgency) * weight(trend). Rango posible: 1 a 125.
- priority_id -> priorities.id (resultado de buscar `priority_score` en `priority_thresholds`)

`priority_thresholds`:
- min_score
- max_score
- priority_id
- sla_min_days
- sla_max_days
- color

Rangos base (configurables, no quemados en código):
- 1-25 -> Prioridad 3 (verde), sin límite estricto (> 2 meses sugerido)
- 26-74 -> Prioridad 2 (naranja), 1 a 2 meses sugerido
- 75-125 -> Prioridad 1 (rojo), ≤15 días sugerido

Técnica de priorización, no es requisito textual de la norma, pero es compatible con el enfoque basado en riesgos (cláusula 6.1). El `priority_score` se recalcula en el Service cada vez que cambian los niveles GUT del Plan.

## Clasificación PHVA en `actions`
- phva_stage (Enum técnico fijo: plan, do, check, act) — clasifica la actividad según el ciclo Planificar-Hacer-Verificar-Actuar (base estructural de ISO 9001:2015, cláusula 0.3.2).
- cycle_number (entero, default 1) — el ciclo PHVA es iterativo: un Plan puede repetir Planear→Hacer→Verificar→Actuar varias veces. Cada Acción pertenece a un ciclo específico, independiente de su `phva_stage`. Permite implementar la vista "Ver actividades anteriores" filtrando por ciclos previos.

## Presupuesto
- actions.budget_planned
- follow_ups.budget_executed

## Avance del Plan
- action_plans.completion_percentage (cacheado, recalculado en el Service a partir del avance registrado en `follow_ups` de las Acciones del Plan)

## Catálogos condicionados en cascada (Fuente -> Ente de Control -> Aseguradora)
- `control_entities`: catálogo de entes de control (Aseguradora, Secretaría de Salud, INVIMA, etc.)
- `insurers`: catálogo de aseguradoras (EMSSANAR, ASMET SALUD, NUEVA EPS, etc.)
- `action_plans.control_entity_id` (nullable) -> control_entities.id
- `action_plans.insurer_id` (nullable) -> insurers.id

Regla: `control_entity_id` solo es obligatorio si `sources.code = 'external_audit'`; `insurer_id` solo es obligatorio si `control_entities.code = 'insurer'`. Validación condicional en FormRequest/Service, no en base de datos.

## Pantallas de Actividades/Seguimientos por tipo de Plan (Corrección vs PA)
El sistema viejo mostraba menús separados ("Actividades de Corrección"/"Seguimientos de Corrección" vs "Actividades de PA"/"Seguimientos de PA"). No se crearán tablas físicas separadas: se usan las mismas `actions` y `follow_ups` para ambos casos, filtrando por `action_plans.action_plan_type_id` (CR vs AM/AC) a nivel de Controller/Service. Evita duplicar esquema.

## Decisión sobre "Acción Preventiva" (heredado del sistema viejo)
ISO 9001:2015 eliminó la cláusula formal de Acción Preventiva; fue sustituida por el enfoque basado en riesgos (cláusula 6.1 / Anexo A.4). Por lo tanto:
- `action_plan_types` NO incluirá un tipo "Preventiva" para nuevos registros.
- Los casos preventivos se gestionarán desde el dominio Riesgos (un Riesgo genera un Caso/Plan con tipo AM o AC según corresponda).
- Si se migran datos históricos con tipo "Preventiva", se mapearán a un valor de catálogo legado de solo lectura (`is_legacy = true` en `action_plan_types`), sin permitir su selección en formularios nuevos.

## Equipo de proceso (`process_users`)
- process_id
- user_id
- role (Enum técnico fijo: owner, member)

Regla: al crear una entidad ligada a un proceso (Plan de Acción, Acción, Documento, Riesgo, etc.), los selectores de responsable/participante deben filtrarse únicamente entre `processes.responsible_user_id` y los `user_id` de `process_users` para ese `process_id`. Esta lógica se implementa en el Service del dominio, no como restricción de base de datos.

## Participantes múltiples (`action_participants`)
Pivot: action_id, user_id. Una Acción tiene un `responsible_user_id` principal y, opcionalmente, participantes adicionales.

## SLA / plazos de cierre
- workflow_transitions.sla_days (nullable): días máximos permitidos entre que una entidad entra a un estado y debe transicionar al siguiente. No es requisito textual de la norma, pero es coherente con el enfoque de procesos (cláusula 4.4) y seguimiento (cláusula 9.1).

# Instrucciones para IA

- Generar una migración por tabla.
- Agregar foreign keys.
- Crear índices necesarios.
- Utilizar constrained() cuando aplique.
- No duplicar catálogos.
- Aplicar SoftDeletes solo en entidades de negocio.
- Utilizar json únicamente para metadata externa.
- Utilizar `responsible_user_id` para asignaciones de responsabilidad hacia la tabla `users`.
